# Contributing

Read the [build guide](docs/building.md), [source guide](docs/source-guide.md), [patch catalogue](docs/patch-catalogue.md) and [test guide](docs/testing.md). Make changes in the module that owns the feature so its complete behavior stays in one place.

1. Identify the behavior and its owner in `engine/features/`. Keep original mission restrictions, cooldowns, difficulty and saved-state semantics unless the change intentionally adjusts them.
2. Make a focused source edit. Assembly generators should expose dependencies explicitly, check the instructions they replace, and stay inside declared memory ranges. Avoid source-text rewriting and hidden dependencies on earlier builds.
3. Run the relevant execution tests, then `python -B test.py`. Tests model original call boundaries; an emulated check is not a substitute for playtesting.
4. Inspect integrity changes with `python -B engine/source_integrity.py`. After reviewing them, use `--refresh` to update hashes. Add genuinely new build files explicitly to both the source manifest and `source-export.json`.
5. Rebuild from supported originals in a fresh output directory. An intentional machine-code change also requires reviewing the affected expected output hashes; never refresh a failed executable/helper/template check merely to make it pass. Check snapshot compatibility before accepting any memory-layout or code change.
6. Playtest the affected behavior and record a concise changelog entry. State what was tested and any remaining limits.

`feature_plan.py` owns required build order. Dependencies between the renderer, HUD, Options and campaign lifecycle are real runtime contracts; merging files must not erase them. `patch-audit.json` records writes and overlap for inspection, but is not proof that all runtime reads are safe.

The export is a byte-for-byte selection of maintained sources. `export_source.py` uses an explicit list and narrows only the source hash inventory. Do not add game inputs, generated headers, binary outputs, logs or private historical comparisons to that list.

Independently authored project code and documentation use the [MIT license](LICENSE). By submitting a contribution to that material, you offer it under the same terms and retain your own rights. No copyright assignment or separate contributor agreement is required. Identify the origin of borrowed code and preserve its notices; original game material and third-party components retain their existing terms. Component notices are recorded in `docs/launcher-third-party.txt`. Dependency review and final publication acceptance remain release tasks.

## Writing source that others can follow

Begin each feature with the problem it solves and a short explanation of its
approach. Comments should explain decisions, caller assumptions and unusual
instructions. Refer to functions and behavior by name. Development revision
numbers belong in private records; fixed compatibility IDs and filenames remain
where saved-state or package formats require them.

The [test guide](docs/testing.md) explains the evidence behind fixtures and build
guards. Add a local explanation when a new test uses a different source of truth
or models an original function with a limited substitute.

Python formatting uses YAPF 0.43.0 with the checked-in `.style.yapf`: four-space
indentation and a 100-column target. Install it separately with
`python -m pip install yapf==0.43.0`, then run
`python -m yapf --style .style.yapf --in-place path/to/changed_file.py`.
Formatting is optional tooling, not a game or build dependency.

YAPF formats Python structure; assembly inside strings needs separate care.
Keep instructions on separate source lines where practical. Adjacent Python
strings join automatically and can preserve the exact assembler input while
making a long routine readable. Keep labels close to their branches and explain
register, stack and state ownership at the routine boundary. After formatting,
compare behavior and generated bytes using the same checks as any source edit.
